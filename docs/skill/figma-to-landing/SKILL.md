# Figma → Landing (с верификацией)

## Входные данные

| Параметр | Обязателен | По умолчанию |
|---|---|---|
| `FIGMA_URL` — ссылка на макет (страница или фрейм) | да | — |
| `REFERENCE_URL` — готовый лендинг, сделанный вручную | нет (если нет — сверка только с Figma) | — |
| `STACK` | нет | статика: HTML + CSS (переменные из токенов) + немного vanilla JS |
| `OUT_DIR` | нет | `./landing-<slug>` |

Если нет `FIGMA_URL`, спроси его. Остальное не спрашивай, бери значения по умолчанию.

## Главные правила

1. **Источник истины — Figma.** Эталонный лендинг — второе мнение, а не образец для копирования.
2. **Слепая сборка.** До фазы 7 не открывай `REFERENCE_URL`: ни скриншоты, ни HTML, ни CSS, ни картинки. Иначе проверка бессмысленна.
3. Тексты, цвета, шрифты, размеры берутся только из Figma. Ничего не выдумывать. Если данных нет, оставь `TODO` и запиши в отчёт.
4. Код из `get_design_context` — только референс. Адаптируй под выбранный стек и токены, дословно не копируй (там по умолчанию React + Tailwind и абсолютное позиционирование).
5. Верстай секциями сверху вниз и проверяй каждую секцию скриншотом до перехода к следующей.
6. Сначала сделай самое экономное: `get_metadata` и `outline.mjs`. Тяжёлые вызовы (`get_design_context`) делай по одной секции.

## Фаза 0. Подготовка

1. `whoami` через Figma MCP. Если не авторизован, вызови `mcp_auth`, затем повтори.
2. Разбери `FIGMA_URL`: `fileKey` — после `/design/`; `node-id=1524-13629` → `nodeId = 1524:13629`. Для URL с `/branch/<branchKey>/` используй `branchKey` как `fileKey`.
3. `create_session` (fileKey + короткое описание задачи). Полученный `sessionId` передавай во все вызовы Figma.
4. Перед первым `get_design_context` прочитай инструкцию `figma-design-to-code` (скил `/figma-design-to-code` или ресурс `skill://figma/figma-design-to-code/SKILL.md`). Без неё инструмент работать не должен.
5. Установи инструменты проверки один раз:
   ```bash
   cd <папка скила>/scripts && npm i && npx playwright install chromium
   ```

## Фаза 1. Инвентаризация макета

1. `get_metadata` для `nodeId` из URL. Ответ обычно очень большой, он сохранится в файл. Не читай его целиком. Сожми скриптом:
   ```bash
   node <скил>/scripts/outline.mjs <файл-с-ответом> --depth 3 --json OUT_DIR/figma/outline.json
   ```
2. Определи:
   - **Брейкпоинты:** фреймы с числовым именем (`1920`, `1728`, `1440`, `1024`, `768`, `360`). Скрипт выводит их в блоке «Кандидаты».
   - **Секции** каждого брейкпоинта: прямые дети фрейма, сверху вниз (по `y`).
   - Вспомогательные узлы (иллюстрации, компоненты, тултипы) не секции. Это ассеты.
3. Если ссылка ведёт на один фрейм, брейкпоинт один. Адаптив делай по правилам из фазы 5.
4. Запиши `OUT_DIR/figma/sections.md`: таблица «секция → nodeId на каждом брейкпоинте → размер». Дальше работай по ней.

## Фаза 2. Токены

1. `get_variable_defs` вызывай **на фрейме** брейкпоинта (`nodeId` фрейма), а не на странице (canvas) или целом разделе. Для страницы инструмент отвечает «nothing selected».
2. Создай `OUT_DIR/css/tokens.css`:
   - цвета → `--color-*` (имя токена Figma `text/text-default` → `--text-default`);
   - типографика → классы или переменные: семейство, размер, межстрочный, letter-spacing, вес;
   - радиусы, отступы, эффекты (blur) → переменные.
3. Подключи шрифты по именам из токенов (Google Fonts, если шрифт там есть). Если шрифта нет, добавь fallback и запиши в отчёт.
4. В остальном CSS используй только переменные. Значения вне токенов допускаются, только если их нет в Figma. Помечай их комментарием `/* из макета, нет токена */`.

## Фаза 3. Ассеты

1. Для каждой секции: `download_assets` (даёт `rawImages` и `svgAssets`, максимум 20 на узел, ссылки временные, качай сразу `curl -L`).
2. Фоны и иллюстрации, собранные из слоёв (эллипсы, группы), экспортируй целиком: `download_assets` для узла с `defaultFormat: "png"`, `defaultScale: 2`.
3. Именуй осмысленно: `hero-bg.webp`, `icon-gift.svg`, `faq-question.webp`. Растр конвертируй в WebP, если это не ломает прозрачность и качество.
4. Не используй картинки с других сайтов, в том числе с `REFERENCE_URL`.

## Фаза 4. Десктоп

Для каждой секции главного (самого широкого основного) брейкпоинта:
1. `get_design_context` по `nodeId` секции. Если ответ слишком большой и пришли только метаданные, вызови его для вложенных узлов. `forceCode` не включай без необходимости.
2. `get_screenshot` секции, затем скачай PNG по присланной ссылке (`curl`), `maxDimension` = высота секции. Сохрани в `OUT_DIR/figma/sections/NN-name.png`.
3. Сверстай секцию. Требования:
   - семантика: `header`, `main`, `section`, `footer`, один `h1`, остальные заголовки по иерархии;
   - гибкая вёрстка: `max-width` контейнера и `flex`/`grid`, не `position:absolute` для всей секции. Абсолют допустим для декоративных иллюстраций;
   - интерактив (аккордеон FAQ, меню, кнопки) работает с клавиатуры;
   - у картинок `alt` (у декоративных пустой `alt=""`), размеры `width`/`height` заданы;
   - `loading="lazy"` для всего, что ниже первого экрана.
4. Подними сервер: `npx --yes serve OUT_DIR -l 4173` (или `python3 -m http.server 4173`). Сними секцию Playwright-ом и сравни со скриншотом секции. Расхождение больше 3% → исправляй, не переходя дальше.

## Фаза 5. Адаптив

1. Для каждого брейкпоинта из `sections.md` получи `get_design_context` и `get_screenshot` секций там, где макет отличается (мобильная версия обычно перестраивается: порядок, колонки, дополнительные блоки).
2. Реализуй через `@media (max-width: …)` (подход desktop-first) или `min-width`. Значения между брейкпоинтами должны плавно масштабироваться (`clamp()`, `%`, `fr`).
3. Отдельные блоки только для одного брейкпоинта (например, «Block dates» на 360) делай в том же HTML и переключай CSS-ом.
4. Для сверки сохрани полностраничные PNG макета для каждой ширины в `OUT_DIR/figma/<ширина>.png`:
   `get_screenshot` на фрейме брейкпоинта, `maxDimension` ≥ высоты фрейма (иначе картинка уменьшится и diff будет шуметь), скачать через `curl`.

5. Переносы строк в тексте сверяй по полноэкранному PNG макета, а не по коду из `get_design_context`: дизайнер часто ставит ручные переносы. Добавляй их как `<br class="m">` только для нужного брейкпоинта. См. «Известные грабли» в `reference.md`.

## Фаза 6. Проверка по Figma (ещё без reference)

```bash
node <скил>/scripts/compare.mjs --built http://localhost:4173 \
  --figma-dir OUT_DIR/figma --widths <список ширин> --out OUT_DIR/report-figma
```

Цель: `built↔Figma` ≤ 5% на каждой ширине, высота страницы отличается не более чем на ±2%, нет горизонтального скролла, ровно один `h1`, нет битых картинок.
Смотри `report.md` → «худшие полосы» и открывай `diff-built-vs-figma.png` для проблемных ширин. Исправляй, пока не уложишься. Не больше 3 итераций, дальше фиксируй остаток в отчёте.

## Фаза 7. Сравнение с эталонным лендингом

Только теперь можно открывать `REFERENCE_URL`.

```bash
node <скил>/scripts/compare.mjs --built http://localhost:4173 \
  --reference <REFERENCE_URL> --figma-dir OUT_DIR/figma \
  --widths <список ширин> --out OUT_DIR/report
```

Скрипт строит три сравнения: `built↔Figma`, `built↔reference`, `reference↔Figma`, плюс сравнение видимого текста и базовые проверки качества.

### Как трактовать расхождения

| built↔Figma | reference↔Figma | built↔reference | Вывод | Действие |
|---|---|---|---|---|
| мало | мало | мало | всё совпало | ничего |
| много | мало | много | ошибка в built | исправить |
| мало | много | много | ручной лендинг отклоняется от макета | **не править**, записать в отчёт |
| много | много | много | разберись по полосам | смотри `worstBands`, решай по каждой полосе |

Дополнительно по тексту: «нет в built, есть в reference» может значить пропущенный блок (исправить) или правку копирайтинга уже после макета (в отчёт).

### Цикл исправлений
До 3 итераций: берём 3 худшие полосы → причина (отступ, шрифт, размер картинки, пропущенный элемент) → правка → повторный `compare.mjs`. Не меняй сборку «под reference», если built уже совпадает с Figma.

## Фаза 8. Итоговый отчёт

Положи в `OUT_DIR/REPORT.md` и коротко перескажи пользователю:

1. Что сделано: секции, брейкпоинты, стек, команда запуска.
2. Таблица диффов по ширинам (из `report.md`) и вердикт `PASS/FAIL`.
3. Расхождения с Figma, которые остались, и почему.
4. Расхождения reference с Figma (то, что ручная версия сделала иначе).
5. Что не удалось взять из макета (шрифты, анимации, ассеты), и что нужно от человека.
6. Что узнали нового. Добавь в `reference.md` раздел «Известные грабли», если встретилась новая.

## Критерии готовности (PASS)

- `built↔Figma` ≤ 5% на всех ширинах. `built↔reference` ≤ 5% или каждое превышение объяснено в отчёте.
- Нет горизонтального скролла, один `h1`, нет битых картинок, нет ошибок в консоли.
- Видимые тексты совпадают с макетом.
- Все секции и брейкпоинты из `sections.md` реализованы.

Подробности, примеры и известные проблемы: [reference.md](reference.md).
